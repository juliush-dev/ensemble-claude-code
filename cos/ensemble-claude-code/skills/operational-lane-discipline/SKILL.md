# Operational lane discipline — advancing lines in parallel without collision

Moment-loaded, retrieve-at-need — **not always-on law**. The always-on worldview deliberately carries no lane text yet; every fold into it (convergence joining the hard-gate family, lane-relative registry/retrieval/capture notes, the amnesia authority refinement) is deferred on-trigger. Read this runbook at the lane moments; settle the *meaning* of the protected terms against `Vocabulary.md` and the Shared External Brain canon note, never from here — this surface is **method**, not the meaning of record.

## The concept in one breath

An **operational lane** is a project-bound operational-state object (supporting cast, beside notebook and effect), not a work unit — the closed five-kind list is untouched. Every project begins with one lane; **"main" names a role and authority position**, not an ontological kind. Work is **sequential within a lane, parallel across lanes**. A lane carries a **focus** (why it was initiated — orientation and bounds, never a closed membership list) and **contents** (the units and effects legitimately advanced there afterward, unpredictable lineage included). Each lane belongs to exactly one project, whose face shows its operational topology.

**The compact authority rule (verbatim, load-bearing):**

> Each lane is authoritative and citable for its own unintegrated operational state. Its state becomes authoritative for another lane only through accepted convergence.

## Lane-placement judgment — at every substantial work-unit designation

Derive a recommendation and surface it; the user is the authority. **Never silently create a lane, never silently assume the current lane.** The named factors:

- interference with the current lane's focus
- mutable-state collision
- body-change breadth
- independent-sequencing usefulness
- expected simultaneous advancement
- consequential-lineage likelihood
- acceptance/integration clarity

Explicit user-requested initiation is available any time, factors or none.

## Initiation — a two-sided transaction

Initiation is a short **two-sided transaction** that establishes a new isolated lane from a **named state of an existing lane** (main or secondary), recording the source lane and source commit. First realization: `git worktree add` from that named state.

**The initiation invariant (verbatim, load-bearing — adopted 2026-07-12 on the user's word, born of the first lane initiation's lived failure window):**

> A secondary lane may not begin substantive work until its initiation is durably and inspectably recorded on both sides: the main-lane topology entry is committed, and the secondary lane's local declaration is committed.

The transaction, in order:

1. Establish the clean source state.
2. Create the lane (`git worktree add` from that named source state).
3. Write the lane's **lightweight declaration** in the lane's own state — identity, source lane, source state/commit, declared focus, reason isolation was chosen, isolation mechanism, bounds/focus guard, status, anticipated convergence target when known. (No notebook slot — lane-hood is not unit-hood.)
4. Write the **topology-registry line** in the main lane (see below).
5. Commit both initiation records in their respective lanes.
6. Only then begin the first lane work iteration.

This closes both failure windows: a lane advancing while main's topology map is still uncommitted, and main claiming a lane whose own declaration is not yet durable.

**Held-automation watch (2026-07-19 gate).** Lane scripts are deliberately held — this transaction runs by hand. At every initiation, re-surface the held-scripts question to the user if any step slips, runs out of order, or produces friction: the slip itself **is** the held trigger firing, surfaced in the moment with this gate's provenance, never silently absorbed.

## Focus guard — three-way, while working in-lane

- **in-focus consequence** → stays; designated in-lane.
- **adjacent-but-uncertain** → placement surfaced before advancement.
- **out-of-focus** → never silently absorbed.

All work-unit truth born in-lane — designations, registry lines, captures, handoffs, gaps, iteration records, body effects — stays in the lane's state until accepted convergence. **Cross-lane inspection** is lawful where the mechanism permits and is neither mutation nor adoption; cite it as "lane X currently records S," which settles what lane X contains, never the project's integrated truth.

## Convergence — target-lane acceptance-gated

**The law:** convergence requires an explicit acceptance decision at the **target-lane boundary**. In this COS **all** convergence is human-gated (main may carry a stricter realization; secondary-to-secondary is never ungated). The Examiner may **prepare** the convergence assessment — proposed integration, still-live units and their placement validity, conflicts, exclusions, target-lane focus and state coherence, provenance survival — but the assessment **feeds** the gate, never replaces it. What converges is **accepted advancements**, not necessarily every artifact; rejected experiments may stay preserved evidence without entering. After convergence the source lane ceases independent advancement.

## Endings — lanes never "discharge"

"Discharge" is pursuit vocabulary. A lane-ending request, and equally the discharge of the initiating focus, surface the **same four-way choice**: converge to a named target / remain live for consequential work / suspend-preserve / close without integration (reason recorded). Lifecycle working names (first-realization candidates): **proposed, initiated, live, convergence-ready, converged, suspended-preserved, closed-without-integration**.

## The lane-topology registry — main-lane face

**Instantiated at the first secondary lane's initiation** — do not create the file before then. **Lane grain only:** identity, status, source lane + initiation state, declared focus, isolation mechanism, current head/inspectable-state reference, intended or actual convergence target, readiness/unresolved integration concerns, final outcome. It **points into lanes, never mirrors their internal work units**, and updates at the named lifecycle moments only — initiation, suspension, convergence request, convergence, abandonment/closure — the one governed topology-grain boundary crossing, never a channel for work-unit contents to leak piecemeal into main. The collision-safe mediation of that crossing is open engineering (the concept requires the update without assuming secondary-lane agents directly edit main's files).
